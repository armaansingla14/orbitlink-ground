# OrbitLink ground

OrbitLink is ground-station software for a CubeSat mission. It was developed
and exercised in simulation only, against simulated passes and links. It
decodes the same CCSDS-style packets as the companion flight software
(`cubesat-flight-software`), so a ground frame is bit-identical to one built
by the C++ encoder. A test checks a vector generated by that code.

## Features

- **Telemetry ingestion**: byte-stream deframer (ASM sync, FECF check, resync), space packets with CRC-16, and decoding of housekeeping, ACK and event packets into engineering units. Raw frames and decoded points are stored.
- **Health monitoring**: yellow/red limit bands with persistence filtering (escalations need N samples, recovery is immediate). Alerts are raised on limit escalation, SAFE-mode entry, spacecraft resets (boot-count change), FDIR events and command rejections. Alerts can be acknowledged.
- **Commanding**: a command catalogue (mode, parameter, capture, power rail, ping), TC packet building, stop-and-wait uplink with ACK matching by sequence count, timeouts and retries. Two queue policies are included:
  - `FifoQueue`: the baseline. Strict arrival order. A command that times out is resubmitted at the tail with a new sequence count.
  - `PriorityRetryQueue`: four priority classes with aging so nothing starves. A timed-out command is retransmitted immediately with the *same* sequence count (up to 3 times), then backs off for 15 min. Multi-frame commands are not started if they cannot finish before LOS.
- **Orbit and passes**: SGP4 via the `sgp4` package, initialised from mean elements with `sgp4init` or from a TLE. A two-body propagator with secular J2 terms is the fallback and cross-check. TEME to ECEF uses GMST. Look angles, AOS/LOS by bisection on the elevation mask, max elevation, and greedy de-confliction of overlapping contacts across stations.
- **Mission timeline**: contact entries are written automatically for scheduled passes. Operators can add their own entries.
- **Event log**: every ingest, uplink, ACK, timeout, limit transition and alert is logged.
- **Storage**: plain SQL with no ORM. SQLite is used for tests and local runs. The PostgreSQL schema and migration are in `db/migrations/001_init.sql`.
- **Dashboard**: React + TypeScript (Vite). Stat tiles, telemetry trends with limit zones and hover readout, a 24 h contact timeline per station, the command queue with submission form, alerts with acknowledge, and the event log. Charts are hand-written SVG.

## Layout

```
orbitlink/      ccsds.py protocol.py limits.py commands.py orbit.py passes.py
                db.py service.py api.py linksim.py
db/             schema_sqlite.sql, migrations/001_init.sql (PostgreSQL)
frontend/       Vite + React + TS dashboard
sim/            run_turnaround.py (queueing experiment), demo_feed.py (live feeder)
tests/          pytest suite (SQLite; PostgreSQL tests behind ORBITLINK_TEST_PG)
results/        experiment output
```

## Running

```bash
pip install -r requirements.txt
python -m pytest                                     # 34 tests on SQLite (+3 PostgreSQL tests skipped)
uvicorn orbitlink.api:app --port 8000                # API (+ dashboard if frontend/dist exists)
python sim/demo_feed.py --url http://localhost:8000  # simulated spacecraft feeding telemetry

cd frontend && npm install && npm run build          # or `npm run dev` (proxies /api to :8000)

docker compose up --build                            # PostgreSQL 16 + API serving the dashboard
```

What was verified in this repository:

- `npm run build` compiles cleanly (`tsc -b` + Vite).
- The API ran under uvicorn with the demo feeder posting about 330 frames.
- The PostgreSQL migration was applied in a `postgres:16-alpine` container, and the suite passed against it (`ORBITLINK_TEST_PG=... pytest`: 37 passed).
- The API Docker image and the full `docker compose` stack were **not** built or run here.
- The dashboard was only checked by building it and querying the API endpoints it uses. It was not rendered in a browser here.

## Results (simulated)

Command: `python sim/run_turnaround.py --days 55 --seeds 3 --loads 0.25 0.4 0.55 0.7`
(about 70 s). Full tables are in [`results/turnaround_summary.md`](results/turnaround_summary.md).
Per-run data is in `results/turnaround_*.csv`.

### Setup

- **Contact plan**: 1162 passes were predicted with SGP4 for a 525 km sun-synchronous orbit over 55 days at Toronto, Svalbard (5 deg mask) and Punta Arenas. That gives **1129 scheduled contacts** after de-confliction, 139.8 h in total. Median contact is 7.7 min, median max elevation 34.5 deg.
- **Link**: 2 s per TC frame, 6 s ACK timeout. Frame loss comes from a link-margin model that depends on slant range and elevation, plus per-pass fading and per-frame scintillation. The spacecraft model suppresses a retransmission of its last executed sequence count, like the flight software.
- **Traffic**: Poisson arrivals. 10% critical, 20% high, 50% normal (1-3 frames), 20% bulk (10-40 frames). "Load" is offered frame time divided by total contact time.
- **Fairness**: both policies see identical arrivals and channel noise, over 3 seeds per load. Commands submitted in the final 24 h are excluded.

Turnaround (submission to ACK), in minutes:

| Load | Class | FIFO mean | FIFO P95 | Priority+retry mean | Priority+retry P95 |
|---|---|---|---|---|---|
| 0.25 | all | 67.7 | 218.9 | 60.9 | 200.0 |
| 0.25 | critical | 60.4 | 185.4 | 70.3 | 234.0 |
| 0.40 | all | 104.9 | 303.2 | 70.1 | 237.0 |
| 0.40 | critical | 93.1 | 257.4 | 61.6 | 207.8 |
| 0.55 | all | 582.7 | 1397.8 | 239.7 | 790.0 |
| 0.55 | critical | 530.6 | 1214.5 | 59.3 | 195.1 |
| 0.55 | bulk | 755.8 | 1994.8 | 520.0 | 1057.4 |
| 0.70 | all | 6794.2 | 17285.3 | 8091.4 | 15882.5 |

Duplicate on-board executions (retransmissions whose earlier attempt had
executed but whose ACK was lost), summed over 3 seeds:

| Load | FIFO | Priority+retry |
|---|---|---|
| 0.25 | 2151 | 1288 |
| 0.40 | 2411 | 1331 |
| 0.55 | 2848 | 1353 |
| 0.70 | 2575 | 1053 |

What these runs show:

- **Medium and high load (0.4-0.55).** Priority + retry cuts critical-command turnaround sharply: at 0.55 the mean goes from 530.6 to 59.3 min. Overall turnaround also improves, because the FIFO backlog grows across passes.
- **Low load (0.25).** Priority + retry is *worse* for critical commands (70.3 vs 60.4 min mean). It also gave up on 20 of them after 20 attempts, while FIFO's resubmission never gives up. Two things drive this. Critical commands go first at AOS, when elevation and margin are lowest. And the 15-minute back-off after a failed retry burst often pushes the retry into the next pass.
- **Overload (0.7).** Offered load is above what the lossy link can actually carry, so both queues grow without bound. Priority + retry delivered fewer commands (61,290 vs 63,709) and had a higher mean turnaround. The FIFO numbers are no better in any useful sense: a backlog of about 12,000 commands is still pending.
- **Duplicates.** Reusing the sequence count roughly halves duplicate executions. They are not zero, because the flight software only remembers the last sequence count, and a retry after a back-off is no longer "the last command".

## Limitations

- Everything is simulated. No RF hardware, modem, or real spacecraft was involved. The link model parameters (margin, fading, frame-error curve) are assumptions, not measurements.
- The orbit is a single synthetic SSO, initialised from mean elements. There is no TLE ingestion pipeline or orbit determination.
- Single spacecraft, one antenna per station, greedy contact de-confliction (not an optimal scheduler).
- Only stop-and-wait commanding. There is no COP-1/FARM sliding window, and bulk uploads are not segmented.
- The API has no authentication.
